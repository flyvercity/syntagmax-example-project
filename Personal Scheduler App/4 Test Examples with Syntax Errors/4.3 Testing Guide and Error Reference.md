# 4.3 Testing Guide and Error Reference

## Overview

This testing guide provides comprehensive documentation for validating parser robustness and error detection capabilities. Each error category includes expected outcomes and validation criteria.

---
## 1. YAML Formatting Errors (4.1.1)

### Error Categories

| Error Type | Example | Expected Behavior | Validation Point |
| --- | --- | --- | --- |
| Missing colon | `attrs` instead of `attrs:` | Parser should report YAML syntax error | Error message at line number |
| Indentation | Inconsistent spaces/tabs | Parser should fail or auto-correct | Indent validation enabled |
| Invalid values | `[UNCLOSED` | Bracket/quote mismatch detected | Syntax validation |
| Duplicate keys | `id:` appears twice | Report duplicate key error | Key uniqueness check |
| Unquoted special chars | `derive: no \| maybe` | Escape or quote required | Character validation |
| Invalid booleans | `'maybe'`, `'unknown'` | Only accept 'yes'/'no' or true/false | Boolean type check |
| Missing attributes | Only `id:` present | Warn about missing func, parent, etc. | Required field check |

### Test Execution Checklist

- [ ] Verify error line numbers are accurate
- [ ] Check that error messages are descriptive
- [ ] Validate recovery mode (skip to next requirement vs. abort)
- [ ] Confirm no partial YAML parsing corrupts state
- [ ] Test error messages in multiple locales

## 2. Markdown Table Errors (4.1.2)

### Error Categories

| Error Type | Symptom | Expected Result | Recovery Strategy |
| --- | --- | --- | --- |
| Column count mismatch | Row has fewer/more cells | Report column count error | Skip row or pad cells |
| Missing separator | No `---` divider | Treat as normal text, not table | Warn user |
| Border formatting | Inconsistent `\|` usage | Parse with best effort | Flag as malformed table |
| Empty cells | `\|  \|  \|` (nothing between) | Accept empty cells | Allow but validate |
| Special characters in cells | Unescaped pipes in content | Escape pipe as `\|` | Pre-process before parsing |
| Extra dividers | `\|---\|\|---\|` | Ignore extra pipes | Normalize table structure |

### Test Execution Checklist

- [ ] Verify table is identified or skipped correctly
- [ ] Validate cell content is preserved accurately
- [ ] Check that row/column counts match header
- [ ] Test fallback rendering (plain text vs. table format)
- [ ] Confirm error doesn't affect subsequent requirements

## 3. Code and Formula Errors (4.1.3)

### Error Categories

| Error Type | Example | Detection Method | Remediation |
| --- | --- | --- | --- |
| Unclosed fence | ````json ... (no closing)` | Count fence markers | Report unclosed block |
| Invalid language | `` `invalid-lang-@#` `` | Validate against known langs | Use fallback highlighter |
| Nested fences | ``` inside ``` | Escape or error on nesting | Flatten or reject |
| Unclosed LaTeX braces | `$\frac{a}{b$` | Match brace pairs | Report LaTeX error |
| Invalid LaTeX | `$$...$$$` | Syntax validation | Skip or use raw text |
| Broken inline code | `` `unclosed backtick `` | Check backtick pairs | Flag as text |
| Mixed formatting | ``code + `inline` `` | Disambiguate context | Parse sequentially |

### Test Execution Checklist

- [ ] Verify fence markers are counted correctly
- [ ] Test language-specific syntax highlighting
- [ ] Validate LaTeX formula parsing
- [ ] Check that code errors don't corrupt state
- [ ] Confirm fallback rendering is readable

## 4. ID and Reference Errors (4.2.1)

### Error Categories

| Error Type | Pattern | Validation | Impact |
| --- | --- | --- | --- |
| Invalid format | `REQ_INVALID#123` | Regex: `^[A-Z]+-[A-Z]+-\d+$` | Mark as non-compliant |
| Duplicate ID | Same `id:` in 2+ requirements | Uniqueness constraint | Error: duplicate found |
| Missing parent | `parent:` (empty) | Required field | Warning: orphaned requirement |
| Circular ref | `id: X, parent: X` | Cycle detection DFS | Error: circular dependency |
| Non-existent parent | `parent: FAKE-STK-999` | Cross-reference check | Warning: parent not found |
| Invalid characters | `REQ-PERM@#$%-001` | Character whitelist | Error: illegal character |
| Length exceeded | ID > 128 characters | Length limit | Warning: truncation risk |
| Inconsistent naming | Mix of lowercase/uppercase | Naming convention check | Warning: not normalized |

### Test Execution Checklist

- [ ] Verify ID format validation runs
- [ ] Test duplicate detection across all requirements
- [ ] Validate parent reference resolution
- [ ] Check circular dependency detection algorithm
- [ ] Confirm error reporting shows line numbers

## 5. Attribute and Value Errors (4.2.2)

### Error Categories

| Attribute | Valid Values | Test Case | Expected Error |
| --- | --- | --- | --- |
| `status` | Active, TBD, Proposed | InProgress | Invalid enum value |
| `derive` | 'yes', 'no' | 'maybe_partial' | Unknown derive value |
| `safety` | 'yes', 'no' | 'maybe' | Invalid safety value |
| `func` | Pattern: F_\\w+ | F_CACHE@001 | Invalid format |
| `alloc` | String (module name) | 123-Invalid! | Unexpected characters |
| Multiple values | Single value only | "Active, TBD, Proposed" | Should be one value |
| Empty field | Should not be empty | Empty string | Required field missing |
| Wrong type | String expected | Numeric ID | Type mismatch |

### Test Execution Checklist

- [ ] Verify enum validation for each attribute
- [ ] Test that invalid values are rejected
- [ ] Check error messages include expected values
- [ ] Confirm type coercion doesn't hide errors
- [ ] Validate that errors don't cascade

## 6. Encoding and Special Characters (4.2.3)

### Error Categories

| Category | Issue | Test Vector | Expected Handling |
| --- | --- | --- | --- |
| UTF-8 Multi-byte | Japanese, Russian, Arabic | Mixed script requirements | Preserve and display correctly |
| Invalid escapes | `\x invalid escape` | YAML string parsing | Flag as invalid sequence |
| Control chars | Tabs, newlines in fields | Hidden characters in YAML | Normalize or escape |
| BOM handling | Byte Order Mark at start | UTF-16 or UTF-8 BOM | Strip or normalize |
| Double encoding | `\\u00e9` vs `\u00e9` | Encoding mismatch | Detect and fix |
| Zero-width chars | Invisible Unicode | RTL/LTR marks | Flag or remove |
| RTL text | Arabic, Hebrew | Mixed direction text | Validate display logic |
| Diacritics | café, naïve, résumé | Combining diacriticals | Preserve normalization |

### Test Execution Checklist

- [ ] Verify UTF-8 characters are preserved
- [ ] Test escape sequence validation
- [ ] Check whitespace normalization
- [ ] Validate RTL language display
- [ ] Confirm diacritics are handled correctly

## 7. Structural and Content Errors (4.2.4)

### Error Categories

| Error Type | Detection | Recovery | Severity |
| --- | --- | --- | --- |
| Missing description | Empty `[REQ]` block | Warning: no requirement text | Medium |
| Unclosed brackets | Unmatched `[` or `]` | Flag and highlight | Low |
| Invalid image path | File not found | Warn and use fallback | Low |
| Nested requirements | `[REQ]` inside `[REQ]` | Parse outer only | High |
| Multiple YAML blocks | 2+ `attrs:` sections | Report and use first | High |
| Only punctuation | "!!!???...@@@" | Warning: empty requirement | Low |
| Extremely long text | > 10KB per requirement | Warning: potential performance | Low |
| HTML/XML mixed | `<b>`, `<img>`, etc. | Strip or escape tags | Medium |

### Test Execution Checklist

- [ ] Verify empty requirement detection
- [ ] Test bracket matching and error reporting
- [ ] Validate image reference handling
- [ ] Check nested structure rejection
- [ ] Confirm multiple YAML block handling

## Testing Checklist Summary

### Parser Validation
- [ ] All error types detected
- [ ] Error messages are clear and actionable
- [ ] Line numbers and character positions are accurate
- [ ] No parser crashes on malformed input

### Recovery and Robustness
- [ ] Parser continues after error (not fatal)
- [ ] State isn't corrupted by errors
- [ ] Subsequent requirements parse correctly
- [ ] Error count is accurate

### Documentation
- [ ] All error cases documented
- [ ] Examples provided for each error type
- [ ] Expected behavior defined
- [ ] Recovery strategies documented

### Performance
- [ ] Large files with errors process acceptably
- [ ] Error detection doesn't cause exponential slowdown
- [ ] Memory usage remains bounded
- [ ] Parser timeouts handled gracefully

✓ **Error reporting**: Clear, actionable messages with line numbers

✓ **Documentation**: Complete and accurate for all error types
